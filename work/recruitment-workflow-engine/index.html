A task-workflow engine for recruitment and onboarding

How a reusable workflow template becomes a live run, with ordered tasks, a full task state machine, and tokenised links that let outside vendors act without a login.

C# / .NETState machinesAudit trails

Problem

Recruitment and onboarding are chains of tasks that pass between different people: hiring managers, HR, and outside vendors who don't have accounts in the system.

The work had to be repeatable (the same steps every time), flexible (tasks change hands, get skipped and run late), and auditable (who did what, and when).

How it works

1. A template defines the shape

A workflow template is the reusable blueprint. It lists the tasks, the order they run in, who each task is assigned to, and the due-date rule for each one. A template holds no live data.

2. An instance is the live run

Starting a workflow creates an instance from a template. The instance is the runtime object: the real tasks, for a real person, with real owners and due dates. Templates and instances are kept separate on purpose, so the blueprint stays clean while many runs happen at once.

3. Rules decide who does what, and when

Each task carries assignment, ordering and due-date rules. Ordering decides when a task becomes available. Due dates decide when it becomes overdue.

4. Every task is a small state machine

A task is always in a defined state, and only certain moves are allowed:

  • Completed: the assignee finishes it.
  • Declined: the assignee refuses it.
  • Skipped: it is bypassed deliberately.
  • Expired: its due date passes without action.
  • Reassigned: it moves to a different owner.

Treating these as explicit states, rather than a loose set of flags, is what keeps the workflow predictable when real life gets messy.

5. Outside vendors act through a tokenised link

A vendor doesn't need an account. They receive a secure, tokenised link tied to one task, and can complete it through that link with no login.

6. Every change leaves a trail

Reassignments and changes to task ordering are recorded in an audit trail, so anyone can see how a workflow got from where it started to where it is.

Architecture

Template (reusable blueprint)
   |  start
   v
Instance (one live run)
   |-- Task 1 --> active --> completed | declined | skipped | expired | reassigned
   |-- Task 2 --> (rules decide when it opens)
   |-- Task 3 ...
   '-- Audit trail: reassignments + ordering changes

Vendor link (secure token) --> completes ONE task, no login

Reliability

  • Task state is explicit, so a task is never "sort of done".
  • External access is limited to a single task through a tokenised link, rather than an account with wider reach.
  • Ownership and ordering changes are recorded, so the history can be reconstructed.

Result

A workflow system built end to end by a three-person team and run in production. Adding a new process means describing it as a template, not writing new code.

Employer systems, repositories, work items and client names are deliberately left out. The mechanism is the point.
