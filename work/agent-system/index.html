A multi-agent engineering system, shipped to a team

Eleven specialised agents that carry work from a vague idea to a draft pull request, with access limits enforced in the tool layer and a human on every merge.

AgentsModel Context ProtocolGovernanceTeam tooling

Problem

Most "AI in the workflow" setups are one person pasting tickets into a chat window. That is slow, inconsistent, and nothing structural limits how far an assistant can reach.

The design goals were different. Make AI assistance a repeatable part of daily delivery for a small team. Keep humans in control of the work tracker, the repository, and the definition of "done". And make the system something other developers can adopt, not just its author.

Process

I treated it as a product, not a folder of prompts.

  • The work item is both the input contract and the output record. Briefs, review reports and done-markers are the audit trail in between.
  • The agent system lives in its own versioned repository. Changes go through the same branch-and-pull-request flow as production code, peer-reviewed and merged.
  • It ships as a distributable bundle with team-facing governance documentation and a setup guide that takes a new developer from nothing to a working, least-privilege integration in about ten minutes.
  • Two colleagues besides me now run it in their own daily work.

Architecture

idea            -> Discovery  -> work item + 7-10 child tasks
work item       -> Scoping    -> implementation brief   (read-only)
                   [ human gate: brief review ]
brief           -> Backend, then Frontend
                   [ human gate: implementation ]
changes         -> Reviewer   -> review report
                   [ human gate: code review ]
approved        -> Documentation  |  Tests
approved        -> PR agent   -> DRAFT pull request
                   [ human gate: a teammate reviews and merges ]
merged          -> Tracker    -> closes only on proof

Eleven agents cover discovery, scoping, backend and frontend implementation, review, testing, documentation, cross-cutting fixes, pull request creation and work-item tracking.

Only four of them hold any external access. The other seven read and write files and nothing else.

Implementation

One narrow integration surface

The whole connection to the work tracker and repositories is a single official Model Context Protocol server entry. There is no custom API client and no webhook.

  • The server is pinned to one organisation at launch, so it cannot reach another one whatever the token would allow.
  • The access token is scoped to work items read/write and code read only. No build, release or identity permissions.
  • The token lives in an environment variable. No secret is ever in a committed file.

Access boundaries live in the tool layer

Each agent declares its permitted tools in its own definition. An agent that was not granted a system physically cannot call it. That is a constraint, not a polite request in a prompt.

Four agents with access, each narrow

  • Discovery turns a vague idea into a work item and child tasks through a one-question-at-a-time interview, and keeps the transcript. The one-question rule is the point: it forces the team to reason in systems rather than fill in a form.
  • Scoping turns a work item into a brief and has no write access at all. It only fetches comment history when the description is too thin to work from, a deliberate budget of roughly 10–12K tokens per brief. It halts rather than inventing content when scope is entangled or the item is too large.
  • PR creates draft pull requests only. Pre-flight requires an approved review, clean working trees and a pushed, non-default branch. The description is grounded in the actual diff and commit log, never in what the brief claimed. It prints the description and waits for an explicit confirmation before anything is posted.
  • Tracker closes work under the completion rule below.

Reliability

  • The three-link completion rule. Nothing closes without a completed pull request, a passing test run, and a documentation file that actually exists. Work-in-progress handoff notes are rejected as evidence. This is what stops the system from congratulating itself.
  • Order matters. The state transition happens first and the comment second, so a failed transition never leaves a misleading "closed" comment on an open item.
  • State only moves toward done. The tracker can never reopen an item or auto-close a parent.
  • Draft-only, never auto-complete. The PR agent cannot merge, by design.
  • Agents cannot spawn or call each other. All coordination is through files on disk, so the audit trail is readable by a person and a misbehaving agent writes a bad file rather than triggering a cascade.
  • Permanently human: merges, deploys, production migrations, and marking anything ready for review.
  • Supporting guardrails: architecture fitness validation with six rules, where existing violations are tracked rather than waived, and a self-hosted build agent for the team's pipeline.

Result

An agent system that is in the team's daily delivery workflow, adopted by two fellow developers, and documented well enough that a new developer is productive in about ten minutes.

What it demonstrates is the part that is hard to fake: not "I built agents", but how to bound them, how to make them cheap, how to keep them honest about what changed, and how to ship the whole thing to other engineers as something versioned and reviewable.

Employer systems, repositories, work items and client names are deliberately left out. The mechanism is the point.
